Key Security Achievements

  • Zero SQL injection vectors — Django ORM used exclusively; SAST confirmed no raw SQL strings
  • Argon2id password hashing — PHC winner, resistant to GPU/ASIC attacks (time=2, mem=65536)
  • JWT RS256 with algorithm enforcement — Algorithm confusion attack (PT-001) detected and fixed
  • Full IDOR protection — Every file access verifies ownership server-side (PT-002 detected and fixed)
  • ClamAV antivirus pipeline — All uploads scanned before storage; malicious files rejected
  • TLS 1.3 enforcement — Older TLS versions disabled; HSTS preload enabled
  • Comprehensive audit trail — Every auth event, file access, and admin action shipped to Elasticsearch SIEM
  • MFA enforcement — TOTP (RFC 6238) + WebAuthn (FIDO2) for all admin accounts

Top Findings (Pre-Remediation)

PT-001 JWT Algorithm Confusion (RS256 → HS256) ● High ✓ Fixed
CVSS 3.1
8.1
CWE
CWE-327
CVSS Vector
AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:N
Remediated
2025-01-20

The JWT library accepted HS256-signed tokens when configured for RS256. An attacker who obtained the RS256 public key (publicly accessible) could use it as the HMAC secret to forge tokens with arbitrary claims, including role: "superadmin".

// Attack: forge admin token signed with RS256 public key as HMAC secret
// BEFORE fix: HTTP 200 — admin access granted
// AFTER fix:  HTTP 401 — algorithm not permitted

// Fix applied:
jwt.decode(token, public_key, algorithms=["RS256"])  // Explicit whitelist
PT-002 IDOR on File Download Endpoint ● High ✓ Fixed
CVSS 3.1
7.5
CWE
CWE-284
CVSS Vector
AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N
Remediated
2025-01-18

The download endpoint returned a pre-signed URL for any valid file_id regardless of whether the authenticated user owned the file. User B could access User A's confidential documents by providing the correct UUID.

// Attack: User B requests User A's file_id
GET /api/v1/files/3fa85f64-5717-4562-b3fc-2c963f66afa6/download/
Authorization: Bearer <user_b_token>

// BEFORE fix: HTTP 200 + presigned download URL (IDOR!)
// AFTER fix:  HTTP 404 — "File not found."

// Fix: ownership check before presigned URL generation
if not verify_resource_ownership(file.owner_id, request.user):
    return Response({"detail": "File not found."}, status=404)

Lessons Learned & Future Work
Phase 5 · Post-Assessment Analysis

Key Lessons

  • JWT algorithm confusion is a real and exploitable attack. The assumption that RS256 configuration prevents HS256 attacks was incorrect. All JWT libraries must be explicitly configured with an algorithm whitelist, not just a preferred algorithm.
  • IDOR is the most common and impactful vulnerability class. Every resource endpoint must implement server-side ownership verification. This cannot be assumed to be "handled by the framework" — it requires explicit code at each endpoint.
  • SAST tools reduce but don't eliminate vulnerabilities. Bandit and Semgrep did not detect the JWT configuration issue because it was a library configuration problem, not a code pattern. Manual testing and pentest remain essential.
  • Defence in depth works. The NGINX rate limiter blocked brute force attempts before they reached the application layer, even before the application-level lockout was engaged.
  • Pre-signed URLs are the correct pattern for file downloads. Zero SSRF or direct file access vulnerabilities were found because files are never served via a public URL.
